# `swas_simulation`

[← Repository README](../../../README.md) · [System architecture](../../../docs/SYSTEM_ARCHITECTURE.md)

`swas_simulation` provides the Gazebo-based simulation environment for SWAS. It simulates the BXU, BRU, vehicle representation, cameras, docking markers, and front approach markers, and connects them to the ROS 2 nodes in [`swas_system`](../swas_system/README.md).

## Purpose

The simulation environment allows the BXU software to be tested without physical hardware. It provides the same main ROS topics used by the hardware system, allowing vision, alignment, docking, supervision, and motion-control logic to operate against simulated sensors and a simulated BXU.

The marker-based front approach, docking vision and control, supervisor, and motion control are used in both simulation and hardware. The YOLO-based front-approach pipeline is currently simulation-only.

## Package contents

```text
swas_simulation/
├── config/       # Gazebo–ROS bridge and simulated camera/sensor definitions
├── launch/       # Gazebo scenes and ROS 2 integration launch files
├── scripts/      # Simulation-only battery-lift node and marker generator
└── worlds/       # Gazebo worlds
```

## Simulation architecture

```text
+----------------------+
|      Gazebo sim      |
| - BXU                |
| - BRU                |
| - Vehicle model      |
| - Cameras            |
| - Markers            |
+----------+-----------+
           |
           | ros_gz_bridge
           v
+----------------------+
|      ROS 2 system    |
|  swas_system nodes   |
+----------+-----------+
           |
           v
   /bxu/cmd_vel
```

The Gazebo BXU receives velocity commands on `/model/bxu/cmd_vel`. The bridge maps ROS `/bxu/cmd_vel` to that Gazebo topic.

## Bridged topics

The bridge configuration is [`config/bridge.yaml`](config/bridge.yaml).

| ROS topic | Gazebo topic | Direction | Type |
|---|---|---|---|
| `/clock` | `/clock` | Gazebo → ROS | `rosgraph_msgs/msg/Clock` |
| `/bxu/cmd_vel` | `/model/bxu/cmd_vel` | ROS → Gazebo | `geometry_msgs/msg/Twist` |
| `/bxu/odom` | `/model/bxu/odometry` | Gazebo → ROS | `nav_msgs/msg/Odometry` |
| `/tf` | `/model/bxu/odometry_tf` | Gazebo → ROS | `tf2_msgs/msg/TFMessage` |
| `/bxu/front_camera/image_raw` | `/bxu/front_camera/image_raw` | Gazebo → ROS | `sensor_msgs/msg/Image` |
| `/bxu/front_camera/camera_info` | `/bxu/front_camera/camera_info` | Gazebo → ROS | `sensor_msgs/msg/CameraInfo` |
| `/bxu/docking_camera_0/image_raw` | `/bxu/docking_camera_0/image_raw` | Gazebo → ROS | `sensor_msgs/msg/Image` |
| `/bxu/docking_camera_0/camera_info` | `/bxu/docking_camera_0/camera_info` | Gazebo → ROS | `sensor_msgs/msg/CameraInfo` |
| `/bxu/docking_camera_1/image_raw` | `/bxu/docking_camera_1/image_raw` | Gazebo → ROS | `sensor_msgs/msg/Image` |
| `/bxu/docking_camera_1/camera_info` | `/bxu/docking_camera_1/camera_info` | Gazebo → ROS | `sensor_msgs/msg/CameraInfo` |

## Simulated cameras

| Camera | Resolution | Rate | Topic prefix | Purpose |
|---|---:|---:|---|---|
| Front camera | 1280 × 720 | 30 Hz | `/bxu/front_camera` | Marker-based or YOLO-based front approach |
| Docking camera 0 | 640 × 480 | 30 Hz | `/bxu/docking_camera_0` | Docking marker 0 |
| Docking camera 1 | 640 × 480 | 30 Hz | `/bxu/docking_camera_1` | Docking marker 1 |

The simulated cameras currently use preview pinhole optics. Their fields of view are intended to be replaced with calibrated hardware optics as those become available.

The docking cameras use optical-frame conventions matching their respective camera links. The front camera looks along BXU `+X`.

## Marker assets

The simulation includes two marker groups:

- **Docking markers:** viewed by the upward-facing docking cameras beneath the BRU.
- **Front markers:** viewed by the front camera during marker-based front approach.

The docking-marker target is generated by [`scripts/generate_docking_markers_target.py`](scripts/generate_docking_markers_target.py). It creates an SDF model containing 9 mm ArUco markers from the `DICT_4X4_50` dictionary, including white quiet zones and black marker cells.

Example:

```bash
python3 scripts/generate_docking_markers_target.py \
  --output config/docking_markers_target.sdf \
  --quiet-zone-cells 2
```

## Simulated battery lift

[`scripts/bxu_battery_lift_sim_node.py`](scripts/bxu_battery_lift_sim_node.py) replaces the hardware relay-Pico battery-lift node in simulation.

It subscribes to `/bxu_battery_lift/command`, accepts `LIFT` and `LOWER`, and publishes `/bxu_battery_lift/state`. It does not actuate hardware and reports the requested state immediately.

| Command | Published state |
|---|---|
| `LIFT` | `LIFTED` |
| `LOWER` | `LOWERED` |

This node uses the supervisor’s current topic names:

- `/bxu_battery_lift/command`
- `/bxu_battery_lift/state`

The hardware battery-lift node currently uses `/bxubatteryliftcommand` and `/bxubatteryliftstate`. These names must be aligned across simulation, hardware, supervisor, and launch files.
